# Method — one executable card per call

Facts live in .koi/run/CONTEXT.md. Execution state lives in .koi/board.json. BACKLOG.md is a generated,
read-only summary: never parse or edit it to decide what runs next. No installed skill or Yokai
executable is required; the standalone `junji-board` binary handles validated storage operations. All paths are repository-relative. Never create method files at repo root.

## Board operations

In a Yokai-driven run use `yokai board` instead of `junji-board` for the same commands;
the driver supplies these operations inside the sandbox. No second executable is needed there.

Use `junji-board show`; take its revision. Mutate through apply --revision N --input FILE,
where FILE is a JSON patch containing effort fields (next_action/carry_forward/title), cards keyed
by phase_id (preserve omitted fields), and optional order (all phase IDs exactly once).
Use status PN planning|building|sealing|done --revision N for stage transitions. Stale revisions
require rereading and reconsideration. Never reset a malformed board or read summary as fallback.
New cards get stable identities and todo state. Runtime tier/strategy changes belong in Yokai YAML.

## Per-phase protocol

1. Load CONTEXT including Skills, the active board effort and carry-forward, and DESIGN if present.
   Resume an in-flight card before selecting the first todo card. Two in-flight cards halt.
   Dependencies must be done; explicit blocking reasons halt. Respect human gates and standing
   branch/push directives. If every card is done, point to consolidate or iterate for new work.
2. Read the card description and binding facts. Load matching Must Skills for this role; do not
   load merely Available skills. Ask when a required human decision is unresolved.
3. Plan this card only. Set planning, research the relevant sources and write a Markdown phase plan
   at .koi/run/phases/phase-NN-slug.md (P0 is phase-00). Reuse a unique existing nonempty plan;
   ambiguity halts. Include Goal & scope, Explicitly out, Approach, Risks, Tests, Acceptance and
   Outcome. The phase-plan Status points at the board card; never duplicate authoritative status.
4. Set building and implement only this card, on the fixed branch. Honor DESIGN with the same
   weight as locked decisions. Record adjacent discoveries as follow-ups; do not expand scope
   or execute another card. A sealing card skips implementation and resumes completion.
5. Verify every documented command in CONTEXT's verification bar, from its documented directory.
   Sensor scripts may implement the commands but are optional for standalone Junji. Every command
   must exit 0. Never weaken a failing bar or edit reviewed gate/assessment metadata unattended.
6. Set sealing, write a self-contained plan Outcome, and apply the done claim, concise card outcome,
   phase-plan reference, carry-forward and next_action. Next action is /junji next while unfinished
   cards remain, else /junji consolidate. BACKLOG.md is regenerated by the operation.
7. Make the required conventional commit including implementation, board and method artifacts.
   Honor Standing overrides. Exclude runtime visibility receipts and regenerable noise; do not
   leave deliverables untracked. Verify commit and clean product state. A driver's independent
   on-disk contract verdict remains authoritative; provisional done is not verified publication.

## Optional publication

The board works offline. When publication is enabled, standalone Junji runs
`junji-board visibility verified --phase PN --commit HEAD_SHA` after verification/commit, then `junji-board visibility sync`. During
Yokai execution, never publish from coding turns; the supervisor and host worker own publication.
New cards publish automatically under the reviewed parent; this does not authorize their execution.
Failures stay pending and never change engineering results. Never store credentials in the repo.

## Report

Phase N of M — title. Next action, then one concrete win and verification result. With all cards done,
name /junji consolidate and /junji iterate REQUEST. On a failure state the failed check and cause.
Stop after this card. Keep CONTEXT and METHOD stable; new locks require an explicit decision.
